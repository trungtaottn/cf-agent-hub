## Exact serialized restore envelope bound

Current recovery-command.schema.json restore envelope has operation, workspace_id, capture_id, expected_authority_epoch, operation_id, reason and payload containing nested manifest and ledger objects. Each canonical manifest and ledger is independently limited to 65,536 UTF-8 bytes. They are nested JSON objects, not JSON strings: their internal escaping is already counted, not escaped a second time.

Three slug values are ASCII and at most 128 bytes each. The epoch maximum 9007199254740991 has 16 decimal bytes. The reason has at most 1,024 Unicode code points; worst-case JSON.stringify serialization is six bytes per point (e.g. NUL as backslash-u0000), plus two quotes = 6,146 bytes. Astral Unicode is four UTF-8 bytes per point, and unpaired surrogates serialize to six bytes; neither exceeds that bound. All fixed keys, quotes, separators, braces, operation value, maximal slugs, epoch and reason total 6,693 bytes excluding the two nested object serializations. Therefore the canonical current restore envelope cap is **137,765 bytes = 6,693 + 65,536 + 65,536**.

Reproduction using JavaScript JSON.stringify / Buffer.byteLength (key order does not affect byte size): maximal three slugs, MAX_SAFE_INTEGER, reason String.fromCharCode(0).repeat(1024), payload {manifest:{},ledger:{}} has 6,697 bytes; subtract the two two-byte empty object placeholders. Freeze this executable accounting as a test, including control characters, quotes, backslashes, non-ASCII and astral text. No vague 2x-control-limit approximation.
