## 1. Smallest scope and honest gaps

One Linux-only implementation, invoked independently by two explicitly selected external agents in two worktrees. Each has its own private state directory, existing protected provider association, task/run/fence and opaque checkout-slot mapping. No global reporter, daemon, host orchestrator, task command, lease renewal, automatic enrollment, grants, MCP registration or generic CLI owner operation. A subsequent unsupported-session scenario uses one of these same selected agent contexts; it is not a third agent, third slot or fabricated observation session. Unsupported runtime produces no report and never implies idle/no conflicts. A future view shows unavailable/unknown based on explicit support status, not invented server rows.

B1 genuinely provides four owner routes but explicitly excludes them from `EnabledOperationId`/`createNativeClient.call`; only `listTaskObservations` is in the generic catalog. A cast to `never`, copied bearer from environment, reading SQLite directly or calling unsupported `.call` is not integration.

One source interface gap and one launch-verification limitation remain:

1. There is no owner-specific authenticated transport API. Existing `ProtectedCredentialProvider.acquire`, `assertLeaseBinding`, `runtimeBinding`, and `dispatchRuntimeProof` are genuine usable building blocks, and `native-provenance.protectedAssociationFor` is an internal trusted bridge. A NEW narrow transport is required and must be reviewed.
2. Establish returns CURRENT binding, not an original-operation receipt; it does not echo repository/checkout mapping. This is a launch-verification limitation, **not a demonstrated unsafe B1 admission gap**. `src/config/bootstrap.ts:143–145` revokes/expires runtimes during configuration installation; `src/auth/runtime-proof.ts:currentRuntime` requires runtime authority_epoch equal current config_epoch, nonrevoked online status and unexpired presence. Actual `test/observations/http.test.ts:243–252` tests atomic config invalidation and old owner-status403/old establish401 after restart. A frozen old launch cannot replace its runtime/provenance with newly enrolled proof and still satisfy B2 exact binding. Therefore no new config precondition/wire amendment is demanded. Existing authenticated current configuration epoch read and authorized observation binding read can verify a newly approved launch mapping; those reads are verification evidence, not authority. In-place unauthorized SQL edits are not the supported configuration transition. Add a real Workers test for delayed establish across supported config installation with old frozen runtime, and treat any unexpected admission as a blocker, not a presumed defect.

Actual installed Claude Code hook version/schema is not evidenced in the inspected repository. Section4 now pins a source profile to inspected official public documentation; no live host access is required to implement its offline fixtures. Installed-host/version compatibility remains separate activation evidence; fail unsupported if the real payload differs.

## 2. Approaches and recommendation

A. **Narrow new owner transport**, reusing protected-provider and transport helpers; four closed operation mappings only. Smallest implementation; requires careful parity tests because authentication dispatch glue is new. Recommended for B2 source, with explicit review of the new trust boundary.

B. Factor the existing native client's pinned authenticated send into an internal reusable primitive, use it for both clients. Less dispatch duplication but touches the mature generic native path, custody inventory and deterministic bundle bytes. **Not recommended in B2**: a semantic-preserving extraction does not preserve exact source hashes or emitted bytes automatically. Frozen native16/17/18 commitments cannot be asserted preserved from tests of behavior alone. Do not broaden the operation catalog or perform this refactor merely for the reporter.

C. Fake-only core now, leave production bridge deliberately unavailable. This is the honest initial offline milestone if A lacks authorization/review or actual launch mapping cannot be verified. Tests can prove queue semantics without asserting integration. Do not call fake-only source a working authenticated adapter.

Package the reporter as a **separate executable/artifact**, with an independent build entry and no imports into `scripts/native-complete-host-entry.mjs` or generic CLI entry. Reuse existing protected provider methods by ordinary source imports into that separate artifact; do not edit the provider to expose secrets. It is an internal concrete source contract, not evidence that an installed supported reporter/provider distribution already exists. Keep all native source/inventory/build inputs unchanged. Native complete-host ceiling is4MiB; the source integration report gives final margin23,350bytes (not independently remeasured by this design). Even a small shared extraction can change embedded inventory/byte sizes across that boundary. Required regression evidence: frozen16/17 artifacts exact byte/hash equality; unchanged18 source inventory/host output hash and size for the same build inputs; no new owner catalog entries; separate reporter size reported independently. If bundling shared source changes native output unexpectedly, stop and diagnose rather than widening caps or regenerating frozen contracts. A separate artifact with unchanged native build graph is the minimal feasible way to preserve those commitments, subject to actual byte comparison.

No new credential format, helper credential service, token export or provider rewrite is justified. Existing protected storage itself uses SQLite; the prohibition on SQLite/WAL concerns the NEW observation queue, not a rewrite of protected credentials.

Use a discriminated operation-specific `OwnerOutcome`, closed validators, and exact receipt matcher rather than the sketch's umbrella name. A state schema rejects unknown fields and impossible combinations. JSON state stores no root, secret, proof, raw hook fields, stdout, transcript, arbitrary server error, or response request-ID. Opaque configured IDs and provider provenance comparison metadata are not bearer authority; keep them private nonetheless.

`InvocationContext` contains ephemeral configured root, monotonic start/deadline, immutable launch snapshot and provider factory. Absolute root exists only in memory or pre-existing protected external configuration, not new persisted queue/manifest output. Capture one immutable context before parsing/projecting the event; if current launch or provider association changes before dispatch, hold old state and drop new event rather than rewrite it. Queue entries share the exact state binding; reject mixed binding, not normalize it away.

## 4. Hook projection

Source profile reference pin: [official Claude Code Hooks reference](https://code.claude.com/docs/en/hooks#posttooluse-input), inspected2026-11-01 UTC, sections `PostToolUse input`, `PreToolUse input`, and tool tables `Write`/`Edit`/`Read`. These document post-success events, native absolute file paths and the field names below. The inspected Write example also includes optional duration_ms. The schema below deliberately supports a bounded subset; this proposal's immutable SHA pins that extracted source contract, NOT the mutable documentation site's full bytes or a Claude release version. Implementation must check in sanitized synthetic fixtures and this reference/date alongside the profile. Live installed-host compatibility is a distinct later gate; source implementation does not require host access.

Concrete offline profile: successful tool-use notification for exactly `Read`, `Write`, `Edit` with a string file path; host event name `PostToolUse`. Map Read to read-observed and Write/Edit to write-observed; these labels mean reported tool activity, never verified byte changes or filesystem enforcement. Do not parse shell commands, test output, transcripts, tool responses, notebook edits, glob/search results or permission decisions. Unknown event/tool/version => neutral drop/unsupported coverage. Do not output JSON decisions, context, permission denial, summaries or retry instructions to the model.

Pin the source-only profile identifier `claude-posttooluse-path-docs-20261101-v1` in the launch context (not as a hook-supplied authority field). Its accepted top-level JSON object requires `hook_event_name:'PostToolUse'`, `cwd:string`, `tool_name:'Read'|'Write'|'Edit'`, `tool_input:object`; optional `session_id:string`, `transcript_path:string`, `tool_use_id:string`, `permission_mode:string`, `duration_ms:nonnegative-finite-number`, `tool_response:JSON` are parsed within the same total bounds but discarded. Reject additional top-level keys for this closed offline profile. `tool_input` is closed per tool: Read requires `file_path:string`, allows positive safe-integer `offset`/`limit`; Write requires `file_path:string,content:string`; Edit requires `file_path:string,old_string:string,new_string:string`, allows boolean `replace_all`. Never persist content/old_string/new_string or any optional metadata. The sole extracted path is `tool_input.file_path`; it must be a Linux absolute path lexically inside the frozen root, converted in memory to the canonical relative output; relative tool paths are unsupported in this pinned profile. No alternative path fields. This documentation-derived fixture profile is NOT evidence of any installed Claude version; unknown extra metadata remains unsupported until reviewed. Optional metadata subset is a deliberate restrictive choice, not a complete description of all official common fields. A caller typing the identifier or payload does not authenticate a hook/runtime.

Raw stdin max 1,048,576 bytes inclusive; enforce bytes before parse, at most1,024 read attempts (including empty chunks), strict UTF-8, max JSON nesting depth16 and max8,192 JSON nodes, and duplicate-key rejection. Define depth/node counting identically to the reused strict parser and test each exact cap/+1, along with read attempt1,024/1,025 and byte cap/+1. Only the named optional metadata and tool fields outside the projection are discarded after bounded parse, never echoed/persisted. Inner accepted tool shape is narrowly validated; reject conflicting/ambiguous path fields. No raw input logging on error.

Derive relative path against the frozen root only in memory. Accept only an unambiguous contained lexical path; reject traversal, absolute submitted relative form, drive/UNC, backslash/NUL, empty/dot segments, and >1024 UTF-8 bytes. Preserve case and Unicode exactly, no URL decoding. This is a lexical display association, not symlink containment proof; do not claim worktree filesystem mediation. Wrong ephemeral cwd/root disables projection rather than changing the launch binding. `source_oid:null`, omit label in minimum implementation; no git subprocess or content read. Timestamp is local capture time claim, not ordering authority. Ignore hook-provided agent/task/run credentials or identity claims.

Completeness is always `unknown`, even in successful source tests and normal steady state. Lock contention/overflow may drop without acquiring any lock; therefore no durable loss marker can be promised. `reportedLocalLoss` only records loss witnessed while already safely holding the lock, never a claim that all losses are known.

## 5. Durable state and dispatch protocol

Linux, Node 24.22.1 and actual pinned util-linux flock executable/version. An externally configured owner-only 0700 state directory outside worktrees and shared temp roots; fixed `lock`, `state.json`, `state.tmp` only. Check owner/mode, regular files, single link, no symlink components, no-follow opens, before reading. Fail closed on unsafe/shared storage. No same-UID hostile process exclusion or disk-quota guarantee is claimed.

Each invocation independently opens the same stable lock inode 0600. Pass only THAT invocation's FD to a fixed-argv `flock --nonblock <fd>` child, no shell or command string. Child and this parent share that open-file-description; independently launched hook parents do not. Parent retains its descriptor after successful flock child exit until finally. Never inherit one launcher-opened lock FD across hooks, unlink/rename lock, timestamp-steal, or use PID expiry as ownership. Wait boundedly for acquisition child and reap/kill it on cancellation; never leave a child retaining the descriptor. Verify inode consistency under the private-directory threat model.

**Genesis is not missing-state recovery.** Ordinary hook entry requires an existing valid `state.json`; ENOENT is held/unavailable and never auto-establishes. The smallest explicit initialization is a separately authorized, offline setup step using this same state schema: validate/create the private directory and stable lock, acquire it, require neither state nor temp exists, then atomically persist a bound empty `ready` state with session/pending/ownerStatus/lastReceipt null, empty queue and completeness unknown. This is an explicit initialization operation, not a new credential, verified flag or authority receipt. No host invocation may initialize implicitly; no `create:true` provider, enrollment, or hook installation is included. If a previously used state directory is missing state, the operator must treat it as UNKNOWN and use explicit recovery/retirement, not rerun initialization there as if fresh. A crash before genesis durability leaves ordinary hooks unavailable; rerunning initialization needs explicit fresh-launch/setup intent and absence checks, not automatic continuation from the hook. A crash after rename but before directory sync may leave a complete genesis file: initializer refuses existing state; ordinary entry validates and re-fences it before any HTTP. Accidental reinit with existing state/temp is rejected without overwrite, even if state appears empty. No extra marker file or credential format is added to infer deleted history; explicit retirement/reinitialization cannot prove an old pending operation never committed. Source tests create the empty fixture through this initializer; production initialization itself needs the applicable directory/setup authorization and approved launch. A pristine initialized empty state permits the first establish. Present-but-corrupt, unexpectedly absent or partial state does not. This is a process distinction requiring operator intent, not a claim that software can distinguish deleted history from a truly fresh directory without an external record.

Under lock: bounded read+validate existing state; discard only stale fixed temporary after validation; capture projected record if admissible. Max 64 queued projected records and 65,536 serialized record bytes; max one frozen request 32,768 bytes; metadata max16,384 bytes; actual total state JSON max131,072 UTF-8 bytes. Count all JSON escaping/duplication, including pending record copies and last receipt. Reject any individually oversize admission and mark witnessed loss if possible; never prune unresolved pending to fit. Check st_size before allocation and validate actual read length. At most two state files =262,144 logical file-content bytes plus empty stable lock, not physical allocation/heap bound.

**Concrete filesystem/deadline choice:** implement all critical-section state read/write/fsync/rename/directory-fsync/close operations with bounded **synchronous** Node filesystem APIs; check the common deadline immediately before and after each operation. Do not issue asynchronous filesystem mutations in this section and do not race a filesystem promise against timeout. If an operation overruns, it finishes/throws while the parent still owns the lock; only then may the hook return or close the lock. There is no outstanding write/rename/fsync that can execute after unlock. Generation checks protect late network continuations, not already-issued filesystem syscalls. Keep the lock across synchronous cleanup too. Hard process death is handled by atomic-state crash recovery and OS descriptor closure, not a detached asynchronous completion. This deliberately accepts an honest soft-deadline overrun on slow/blocking disk rather than weakening durability/serialization.

For EVERY transition that authorizes network: open fixed temp with no-follow/exclusive semantics after safely removing stale temp under lock, mode0600; write bounded complete state; fsync(temp); rename within same directory to state.json; fsync(directory); only then dispatch. Failed write/fsync/rename/directory-sync => no network. Pending state is durable BEFORE acquiring/using secret bytes for send. Keep lock through response validation and receipt durability using the same atomic protocol. A successful response is not settled until its receipt transition and successor highwater are durable. If final persistence fails before rename, the prior pending normally remains; if rename succeeds but directory fsync fails, the visible/newly recovered state can be either the old pending or a complete new settled state. Do not claim old pending necessarily survives. The current invocation performs no successor action. On restart, validate whichever complete state is present and durably re-fence it through the same temp fsync/rename/directory-fsync sequence BEFORE any network/status/successor operation. A valid settled receipt in the new complete state can be accepted only through this fresh durability fence; old pending stays UNKNOWN and reconciles normally. Missing/invalid state holds. Never select `state.tmp` as an alternative committed truth.

Whole hook shares one monotonic 2,000 ms budget from process entry, including stdin, acquisition, parse, filesystem, provider, transport and settlement. No timer resets per operation. At most one HTTP request per invocation is a simple implementation limit (later invocations progress queue). This includes every transport request; there is no hidden launch/config/task verification HTTP before the owner request. Required authenticated launch/mapping readback is a separate explicit pre-initialization/setup prerequisite, outside ordinary hooks, and its approved opaque comparison values populate genesis. Ordinary hooks recheck the actual protected association and rely on server current-authority guards; they cannot silently fetch extra launch metadata. Before a status-only invocation too, durably re-fence validated state so a previous rename/directory-sync failure cannot authorize progress from unfenced state. Budget exhaustion aborts transport, retains pending and exits neutrally. No background retry/daemon/waitUntil; late callbacks have generation checks and cannot write/unlock successor state. Blocking synchronous filesystem/provider calls and OS scheduling can exceed a userspace timer; a literal hard 2s return guarantee cannot be proven with Node+fsync alone. Activation must verify host timeout/termination behavior and accept this operational bound, or stop for a different approved execution primitive. Do not silently call it a strict hard-real-time guarantee.

## 6. State machine, uncertain results and replacement

- Explicitly initialized validated empty context: persist queued projection plus establish intent. Establish response proves only **current binding**, not original establish execution. Durably transition to `awaiting-owner-status`, clear this establish pending, save matching session ID/epoch with highWater:null and `ownerStatus:{sessionId,epoch,reason:'established'}`; queued events remain frozen. This continuation is durable before unlock and is mandatory even for an apparently new session. Exact protected runtime/provenance and launch verification gates must pass before production dispatch; supported config changes invalidate old runtime authority.
- `awaiting-owner-status`: on a later invocation, make only the owner-status HTTP request for the exact frozen session/runtime. No append, replace or establish is allowed in this phase. Validate session/epoch/highwater and latest receipts; persist a `ready` transition with a known highwater only if it agrees with durable local history. A genesis establish normally requires highwater0 and no unexplained batch/replacement activity. Unexpected nonzero highwater or receipt means hold for explicit coverage-loss recovery, not silently skip unknown activity. Failed/aborted/malformed status retains this continuation. Queued same-binding events may remain bounded or drop, never dispatch. With at most one HTTP per invocation, constructing/sending an append occurs on a subsequent invocation only after the ready transition is durable.
- Ready with session: form prefix batch of <=32 records fitting actual 32,768 bytes; contiguous first sequence highWater+1. Freeze exact path/method/body/fingerprint; persist pending first. Never expand pending by adding later events.
- Known receipt: require exact session, range, count, expected fingerprint and valid timestamps/schema. Persist receipt/highwater/removal of exactly acknowledged prefix atomically. Receipt means diagnostic ingestion only.
- Dispatch exception/timeout/malformed response/cancel/crash/receipt-persist failure: leave pending UNKNOWN. No successor batch/replacement/establish. A new projected event may only join remaining bounded queue under same binding, or be dropped.
- Reconciliation: status exact pending session with current proof; accept only retained matching latest batch fingerprint/range/count and valid highwater. Matching receipt can settle even if reported records were evicted. Missing receipt, higher highwater, guessed success from ordinary read, or later 4xx does NOT settle.
- Optional exact retry is only the same durable append/replacement, same frozen run/session/body with fresh current authority. It is not a new logical operation. Current binding/config changes prohibit retry. A previous canceled remote request may still be executing: one logical pending operation is enforceable, absolute one remote physical request forever is not. Idempotent same-intent replay handles that uncertainty; do not claim network abort rolled back a commit.
- For lost replacement response, old-session status cannot find the new session. Exact replacement retry can recover retained receipt while current authority survives. After any matching replacement receipt (direct or recovered), atomically clear pending and persist `awaiting-owner-status`, new ID/epoch with highWater:null and `ownerStatus:{sessionId:newId,epoch:newEpoch,reason:'replacement-recovered'}`, plus the exact receipt. Retained matching replacement receipt may follow later successor appends; never set highwater0 from its historical epoch-start implication. The next invocation performs owner status only. Continue only when status agrees with durable history; unexplained successor activity is held, not adopted. A second replacement/slot reuse may erase the receipt; UNKNOWN remains. Crash before receipt durability leaves the old pending retry; crash after it resumes owner-status, never an append guessed from epoch start.
- Lost establish may be retried as a CURRENT-binding retrieval only with the exact frozen run/fence/runtime/provenance and unchanged locally approved launch. It does not settle an original establishment operation. Persist the explicit awaiting-owner-status continuation above, then obtain current owner status in a later invocation before assigning sequence numbers: an existing session may have nonzero highwater. If local state has never held an append and authorized status has no unexplained prior activity, continue from verified highwater; otherwise hold for explicit coverage-loss recovery rather than claiming ownership of unknown old batches. A config install invalidates the old runtime and denies retrieval; never switch to a newly enrolled proof to make it pass. Reject a changed session when an old append/replacement is pending; a current establish response must not erase uncertainty.
- Known local coverage loss with no unresolved pending: obtain current exact-owner status, then persist one replacement intent with expected session/highwater and frozen unique replacement_request_id/reason coverage_loss. No automatic replacement just because process started. Keep loss visible and discard old queued records explicitly; never carry them into replacement or new run. A CAS conflict is a hold, not permission to chase current session automatically.
- Missing/corrupt state: do not infer sequence0, reconstruct old payload, or auto-establish. Hold, preserve unknown/loss diagnosis without raw bytes. An explicit scoped recovery may read current owner status and choose coverage-loss replacement only after acknowledging the old operation cannot be proven; this is not a claim to have settled an unknown pending intent. No automatic recovery deletion by hooks.
- Revocation, expiry, changed fence/principal/runtime/config, disablement or restore: stop new sends; retain unresolved state locally at fixed bound; no rebind to successor. Current 401/403/409/503 cannot prove earlier noncommit. Explicit diagnostic retirement may delete state under lock after recording UNKNOWN elsewhere through an approved safe mechanism; never unlink lock.

## 7. Authentication dispatch and response currentness

`FrozenBinding` and `VerifiedPrincipalBinding` are structural comparison constraints only, never authenticated provenance. A cloned JSON object, forged `provenance` member, homemade provider or a `verified:true` flag must not authorize dispatch. In a new hook process, the genuine `ProtectedCredentialProvider` validates the existing OS-protected store, slot/proof rows and registers its private callback with the existing internal WeakMap bridge. Resolve `protectedAssociationFor` for the exact provider instance and acquired lease, compare frozen values, then dispatch via that provider's pinned proof method. Do not add a registrar call for user-supplied metadata; do not restore provenance from observation JSON. This is the existing protected-store validation contract, not a new signed JSON format; no claim is made that the inspected SQLite store itself is a cryptographically signed artifact. Installed source/custody authentication is separately an activation prerequisite. Same-process malicious module import is outside this trusted-code boundary, just as documented in native-provenance.ts.

Recommended A uses concrete protected provider `create:false` for production; fake provider only injected in offline tests. Obtain current registered protected association, compare every principal field, origin/workspace and runtime to frozen binding, acquire exact expected lease. `CredentialProvider` alone has no proof retrieval or durable provenance guarantee: require the protected bridge and explicit proof dispatcher; do not imply arbitrary providers satisfy production contract.

Validate closed route/body, canonical request <=32768 and exact B1 fingerprint computation: SHA256(canonical JSON `{method,path,sessionId: appendSessionIdOrNull,body}`), using actual encoded pathname. Establish fingerprint is only a local identity; there is no establish receipt fingerprint. No new idempotency header for observation operations. Use existing HTTPS origin validation, `credentials:'omit'`, `redirect:'manual'`, `cache:'no-store'`, response-origin checks, bounded <=1MiB JSON and canonical validators. Reject redirects and unsolicited cookies as auth mechanism. Never persist authorization/x-runtime-token.

At actual synchronous dispatch boundary: pin `lease.use`, validate current lease/registered association and exact runtime, invoke `dispatchRuntimeProof` on that same lease, put ephemeral bearer/proof headers, recheck monotonic deadline and frozen binding, then send exactly once inside the callback. Enforce callback invocation once/synchronous-return linkage as native-client does; no async secret callback or captured token later reused. Fresh local currentness checks after awaits and before receipt settlement; if revoked/rotated during response, retain UNKNOWN instead of accepting stale response. Release lease in finally and scrub reference-bearing closures; no logs. Server rechecks current actor/grants/run/proof/config after async work within its transaction—local labels never substitute for that.

Existing protected provider operations may block and mutate its normal storage mechanics; merely opening existing store is not a new enrollment or new credential authorization. Exact provider path and permission to use it are activation prerequisites, not values to infer from another agent's files. Do not actually inspect any real protected store during offline source work.

## 9. Activation prerequisites and stop conditions

Source step can proceed only after independent review/authorization of the chosen new transport; launch verification remains explicitly unavailable until its existing read paths and approved manifest are wired. Finish B1 exact-head publication/CI independently; B2 cannot stand in for it. Offline tests passing establishes source behavior only.

Before ANY real hooks: approved exact B2 revision and mandatory CI; verified Linux/Node/flock/filesystem and real host hook version/payload/neutral timeout behavior; explicit selected two worktrees and existing runtime/provider associations; existing grants including execute/read/events, valid run lease/fence, known matching server mapping/epoch verified through existing authorized reads and an approved launch, authorized nonproduction target; safe private directories and intentional activation permission. No grant/credential/config/install/network/security changes are bundled by implication. If actual supported hook requires settings/install permission, obtain it separately or stop.

Before live acceptance: first one supported context, then both selected contexts, then unsupported session using one of the same contexts; real sanitized receipt evidence, separate UI work if requested, negative stale-owner/cross-scope cases and exact-head full CI. Actual two-agent journey is not satisfied by synthetic event JSON or screenshot.

Stop/report blocker on unsafe directory, missing provider seam/association, unknown host contract, unverifiable approved launch mapping, unachievable 2s operational behavior, pending uncertainty without exact retained receipt, dependency/toolchain failure or authority gap. Immediately disable observation reporting/view intake under separately authorized operational procedure on scope leak, raw secret/content persistence, authority mutation, stale-owner acceptance or unbounded resources; do not cancel tasks or change grants. This design stops at reviewed offline-source evidence, not activation, merge, release or a completed B pilot.
