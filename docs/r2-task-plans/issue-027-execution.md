## Measured query decision and supported limits

The open-source comparison preceded production code. Actual locked Workers research then measured 380 SQL shapes at 1,000/10,000 rows, tied/all-equal timestamps and terminal seeks. Global schema8 ORDER BY/LIMIT read 2,000/20,000 rows; a hidden-only filtered LIMIT 2 read 1,001/10,001. Existing fixed-state seeks and an experimental global index each read at most cap+1; sequence seeks read at most cap. The experimental index was created only in isolated tests: production migration 8 is unchanged, schema remains 8.

Select the existing seven-state indexed merge for this bounded MVP issue. A global index is cheaper and simpler for reads, but a forward schema 9 migration would require updating schema assertions, bootstrap/operator envelopes, full table registry/version contracts and currently-unavailable schema8 recovery ownership. It is not required for correctness: the selected implementation has seven fixed streams, indexed order and explicit work limits, with no scan/sort fallback. This is a documented engineering tradeoff, not evidence that the global index is worse or permission to edit migration 8. A future performance/index amendment can revisit it with recovery/version review.

Select 2,048 private physical candidate examinations per query, tested at 128/512/2,048 and denial at 2,049. Task streams keep one row per state; history batches 32 numeric sequences, resolving one bounded result key at a time. Task streams additionally permit up to seven one-row terminal probes, which may prove end but never authorize/return an extra candidate. Every query also has fixed initial high-water and current-actor costs. Domain row/SQL bounds are not LIMIT-only claims or interruption APIs. Route encryption reauthorization can run the bounded query twice; those costs must be added, not described as one query's cost.

The candidate choice allows four times the hidden-heavy traversal of 512 at linear worst-case authorization work, at an intentional availability/cost tradeoff. Hidden-heavy data beyond the cap returns generic 503 with no partial result/cursor. Larger limits are not auto-selected. Timing and resource-failure side channels remain, and no constant-time, production latency SLA or optimal tuning claim is made. Exact final counters and diagnostic timings are retained with the implementation test receipts.

Memory bounds are separate from row limits. Seven single-row task heads replace an initially investigated 32-row-per-state prefetch that could materialize hundreds of MiB of supported persisted identifiers. History batches numeric positions only. Scalar-byte preflights precede large body reads; hidden result summaries are not materialized before complete artifact visibility. The maximum 1 MiB response uses actual JSON UTF-8/escape sizing and maximum 2,048-character cursor / 36-character request ID overhead. Both result and resulting Task must pass `assertTaskResultAdmissionFits`; future submit/restore owners must integrate that guard. No universal identifier maxLength or new public DTO field is invented.

Current-authority prerequisite correction: human-managed adoption of a static agent enumerates at most the existing canonical 1,000 configured static references and uses indexed current-row point lookups; accumulated historical rows no longer cause an unbounded filtered scan. ## Batched authorization comparison

The initial bounded point-query implementation cost 49,226 SQL statements and 86,033 rows read for 2,048 results with four readable artifacts and a final inaccessible fifth artifact. Bounded was not treated as optimal. The selected replacement batches the schema-constrained maximum five result associations into one indexed outer relation, LEFT JOINs the selected artifact/generation, and computes visibility using scoped primary-key association EXISTS expressions. Visibility is not a WHERE predicate, so hidden rows cannot expand outer enumeration. There is no cached authority across awaits.

Actual final comparison: 14,410 statements and 79,889 rows read for the same negative workload; local plain replay timing changed from 308 ms to 101 ms in the retained comparison, with noisy timers and no CPU/SLA claim. Statement count fell about 71%; rows fell about 7%. The all-five-visible join also preserves the complete ordinal list and fails whole-result visibility when the final association is removed. Literal work assertions use the measured query plan, not an adaptive expected-output calculation. Each actual join/EXISTS uses a scoped index, with no scan or temporary sort in the recorded plan.

This cost is accepted as a supported MVP ceiling rather than a throughput recommendation. The 2,048 cap is explicit and fail-closed; response re-observation around encryption can double it. Official platform limits and their distinction from measured elapsed time are linked in the [research note](../research/r2-task-domain.md).
