# R3 closed decision contract

Status: inactive trusted policy and exact-input source substrate; product actions, runtime integration and acceptance pending; no released artifact.

These partial [issue 52](https://github.com/trungtaottn/cf-agent-hub/issues/52) and [issue 54](https://github.com/trungtaottn/cf-agent-hub/issues/54) source units consume [the reviewed source bridge](r3-handoff.md). It does not activate request-decision, approval routes or claims. The production source action registry is empty. The [decision policy schema](../../spec/decision-policy.schema.json) is an optional structural member of trusted deployment configuration, not permission. Supplying a schema-valid action name, an example or a profile cannot register an action. No configuration is installed by this source change.

## Explicit policy, no product defaults

A policy requires a positive safe-integer revision, positive finite expiry seconds, bounded expiry batch and closed action entries. Each entry names an exact action/schema version/digest, nonempty reviewer IDs and explicit resource kinds. Duplicate action IDs, duplicate reviewers/resource kinds, extra properties and missing bounds fail. Structural validation does not establish that reviewers are humans, currently assigned, permitted to decide, or able to read every input; transaction-current resolution must prove those facts. The configured reviewer IDs are an assigned set, not a candidate pool: any missing, disabled, mismatched or insufficiently authorized configured human denies the entire requirements lookup. There is no silent filtering. This is not a unanimous-vote rule; later individual approve/reject semantics remain separate.

Local contract ceilings are 64 action entries,64 reviewers/resource kinds per entry,128-character identity fields,65536 serialized UTF-8 policy bytes and 200 expiry units per bounded call. These are explicit finite work limits, not measured deployment capacity. Actual expiry values, human assignments and action semantics remain operator-owned; no universal TTL is selected. The [valid example](../../examples/decisions/policy-valid.json) uses synthetic arithmetic values with an empty action list, not recommended defaults. The [invalid test fixture](../../test/fixtures/decisions/policy-invalid.json) demonstrates missing expiry, zero batch and forbidden unlimited mode.

`parseDecisionPolicy` returns detached structural data only. `resolveConfiguredAction` remains unavailable for every action because no product action schemas have been approved and installed. The deployment schema accepts optional `workspace_policies[].decision_policy` with no default. Structural installation may retain well-formed inactive/unknown action, schema-version, digest or resource-kind selections; exact compatibility is checked only during source resolution. Missing bounds, malformed digests, duplicate actions/reviewers/resource kinds and extra fields reject installation. Later activation requires a separately reviewed source descriptor, exact schema and resource/effect semantics, and explicit trusted operator assignments/finite expiry; arbitrary schema URLs, modules or proposal-supplied callbacks are not such a registry.

## Inactive current-SQL requirements adapter

`lookupPolicyRequirements` is the only production policy entrypoint and captures the fixed empty registry. It cannot accept a registry override. A package-internal source composition is exercised only by an isolated test helper; the fixture descriptor is never imported by deployment parsing or a production bundle. All production selections, including `ExampleApprovalInputs` and names resembling native operations, remain `DECISION_UNAVAILABLE`.

The synchronous adapter refreshes the actual native actor, rereads the task ID/version and task/project scope, current installed configuration/installation digests and epoch, maintenance/admission generation, and every proposal/input artifact's committed metadata and complete current association graph. The entire assigned reviewer set must be enabled same-workspace humans at the current epoch with exact installed issuer/subject identity. Their effective scopes/project ceiling are the intersection of installed configuration and current relational grants, never a union. Reviewers need both canonical human `approvals:read` and `approvals:decide`, task/artifact read rights and descriptor-required scopes; every current association must be readable by every assigned reviewer. No reviewer session or authenticated ActorContext is fabricated. Errors remain the same secret-free unavailable result without identifying which reviewer or resource failed.

The two approval scopes are recognized only in `human_grants[].scopes`. This installs no grants, enables no routes, changes no native/delegable scope enum, and adds no display capability. Static native configuration and managed native issuance still reject them. Existing documents without decision policy retain their exact canonical bytes/digests; no historical signed receipt, native fixture or recovery manifest is rewritten.

The returned deeply frozen `DecisionPolicyRequirements` remains explicitly `phase: requirements-only`, **not an eligible final resolution or assignment**. Optional canonical checkpoint references join the proposal/input reference union without creating checkpoint storage. Proposal `scope.resource_ids` are retained exactly but are not assumed to be tasks or interpreted from a resource-kind label. `assertCurrent` rereads source/SQL requirements and enforces the original candidate deadline. Requirements copies do not establish runtime provenance. The separate verifier below owns exact bytes, closed schema/target coverage and private receipt identity; no route, mutation consumer or no-effect producer is supplied.

Source identity includes immutable `semanticRevision` in addition to action ID and exact schema version/SHA-256. Extraction, required scopes, target/version interpretation or effect-boundary changes require a new semantic revision even if JSON schema bytes do not change. Requirements/final interfaces carry separate `generationId: string`, `artifactVersion: number`, `configEpoch: number` and `admissionGeneration: number`; the historical pure `inputGeneration` numeric diagnostic is not native generation provenance. Equality diagnostics do not establish genuine bytes or authority. The standalone opaque verified-input interface itself requires exact workspace/policy revision/canonical policy/configuration epoch/digests/admission identity, not merely an outer resolution. The private verifier and rechecks bind them together exactly. Final-resolution and verified-input interfaces cannot be constructed from candidate/request-shaped data; structural casts, JSON and clones do not establish runtime membership.

All adapter operations are queries: no task/run/approval/event/outbox writes, lease extension, migration or live installation. Tests use the ordinary structural deployment/bootstrap/install path and actual Workers SQL, with existing R2 stage/upload/commit only to prepare readable input metadata; replacement-generation tests are explicitly metadata-only and do not claim replacement bytes. ## Exact input bytes

The canonical Proposal.inputs remains artifact ID plus lowercase SHA-256; no public verified flag or new DTO authority is added. Input MIME must be exactly `application/json`. `inspectProposalBytes` snapshots at most 10485760 bytes before asynchronous hashing, parses that same snapshot and returns its actual SHA-256/byte length and frozen JSON content. Formatting changes change the identity. This output is **not** VerifiedProposalInput: it proves neither committed artifact generation, workspace/access/retention, schema match nor policy provenance. The inactive verifier retrieves bounded bytes and privately binds current complete artifact/generation/association snapshots, exact content and installed policy across synchronous SQL checks and asynchronous R2 reads.

`parseExactJson` rejects invalid UTF-8, a leading BOM, duplicate decoded object member names at every depth (including escaped aliases), invalid grammar and unpaired surrogate escapes. Unicode normalization is not performed. JSON numbers are deliberately narrowed to mathematically exact safe integers; decimal quantities must be explicitly schema-defined strings. Exponent notation representing an exact safe integer is allowed, but underflow/rounding cannot turn a fraction into permission. These numeric/Unicode restrictions are this proposal contract, not claims that RFC 8259 forbids all such JSON.

Required parser budgets can only narrow the hard 10485760-byte/64-container-depth/100000-value limits. Root containers count as depth 1; every value including containers counts as a node, object member names do not. An iterative duplicate/resource preflight precedes native grammar parsing. No dependency or remote reference is fetched. Hashes use original bytes, never reserialized parsed data.

## Inactive private exact-input verifier

`input-binding.ts` is the fixed production entrypoint; its registry remains empty. The package-internal source composition supports only isolated closed test descriptors. `verifyProposalInput(ctx, task, checkpoint, proposal)` pins the original verified identity/admission and workspace/storage/object/bucket/clock references before awaiting. It validates/detaches canonical intent (combined checkpoint/proposal serialization at most 65536 UTF-8 bytes), retrieves only the SQL-selected private generation key, and rechecks fresh trusted time, configuration, actor, every assigned human, reference visibility and complete private native metadata around every get/read/hash await. Source schema validation must synchronously return literal `true` before pure synchronous target extraction. Extracted closed task targets must exactly cover scope IDs; current SQL supplies version/project truth. Summaries are inert and never supply targets.

Only the composition's closure-private WeakMap can establish a receipt. `recheckProposalInput(tx, ctx, task, checkpoint, proposal, input)` checks membership before reading any claimed evidence properties, binds the supplied active transaction to the pinned storage through private transaction-origin identity, rejects forged/escaped/other-storage transactions and copies/clones/Proxy wrappers/other compositions, and rereads current SQL using the original identity and original candidate deadline. Complete row/association changes invalidate the receipt even when reduced public identity fields match. The branded frozen returned resolution is current evidence, **not a reusable execution or external-effect permit**. A future consuming command must call the recheck in its own transaction and independently enforce runtime proof, run/lease/fence/current versions immediately before its writes.

The native BYOB reader coalesces up to 64KiB scratch reads, immediately copies detached views, requires exact count plus EOF, and permits at most `ceil(expected/65536)+1` reads (161 at 10MiB). No default-reader fallback, decompression or reserialization exists. Full guards are capped at `4*maxReads+16`; one 16384-unit reference-work budget spans the actor, all reviewers/targets and every asynchronous guard. Exhaustion is fixed `DECISION_UNAVAILABLE`, not invalid input or a smaller product byte ceiling. Individually legal maxima are not guaranteed jointly: dense reviewer graphs and near-limit bytes may exhaust this shared operational budget.

A separate 30000ms asynchronous deadline races pending get/read/hash work and request cancellation; cleanup is not awaited and late bytes cannot mint evidence. It is **not** a strict synchronous CPU wall-time bound or approval TTL. Deployed Workers `Date.now()` and `performance.now()` can freeze until I/O; deterministic read/guard/reference/parser bounds and intrinsic `scheduler.wait(0)` at least every eight reads and after parse/schema/extraction bound immediate work and allow timers/cancellation/current SQL to progress. Pending promises still require functioning timers or external cancellation. Local tests do not establish deployed CPU timing. Both requirements and final resolution `resolvedAt/expiresAt` are provisional candidate freshness, never admitted approval timestamps; later approval admission must establish its own one-time expiry without renewing an existing approval.

Checkpoint/proposal/input byte accounting retains every role edge while deduplicating identical native bytes across the distinct union: at most five artifacts,10485760 bytes each and26214400 total; per-role ID serialization is at most8192 bytes without within-role duplicates. Nonempty future checkpoint reference roles may name ordinary committed artifacts with supported associations, but existing unsupported `checkpoint` association rows remain denied. This adds no checkpoint table or ownership semantics. The internal combined-intent bound does not preapprove the future complete 65536-byte request envelope including run/fence/version overhead.

## Association accounting amendment

For this new decision contract, retain each existing per-role limit: at most 5 checkpoint artifacts and 5 proposal artifacts, at most 8192 bytes of serialized ID references per list, no duplicate ID within a list, and at most 10485760 bytes per artifact. The input artifact is a separate role edge. Across all three roles the **distinct-ID union is capped at 5 artifacts and 26214400 retained bytes**. Repeated IDs across roles count once only when generation/hash/size agree; every role edge still exists and needs current authorization. This is an explicit new aggregate restriction, not a claim the historical per-list schema already imposed it.

`accountDecisionArtifacts` models finite count/byte consistency. It does not prove actual bytes, commit status, actor/read rights or retention. Later transaction owners must retain/recheck every referenced generation and reject revoked, replaced, missing or contradictory commitments atomically. No retention deletion policy changes here.

## Owner-selected bounded reuse — 2026-10-31

The owner approved reuse only within the original unexpired approval lifetime, with unchanged current policy and exact approved intent/target bindings, and affirmative proof the prior attempt produced no effect. Every fresh attempt receives a fresh run/fence and consumes the ordinary retry budget. Unknown or possibly effected work is held for reconciliation, not automatically resent. Reuse never renews approval; expired authority requires a new approval.

The existing R2 captured replay-safe rule fields and runtime `outcome_unknown=false` do **not** establish no effect. An externally idempotent operation may already have effects. Missing receipts, timeouts, lease expiry or a later refusal cannot erase earlier uncertainty. Trusted evidence must cover every authorization-significant effect of every earlier attempt under that approval, not just the most recent operation.

Immutable authority includes workspace/task/approval, proposal and approval versions, action/schema identity, input artifact generation/hash, policy identity/epoch and exact target-resource versions. Evolving task/run versions are different: each command still supplies the exact current expected version, while permitted claim/failure transitions advance lifecycle versions. The pure model starts at the approved task version and preserves retry count already consumed before approval; it never resets the task budget to satisfy a fixture. Arbitrary metadata/target drift is not an allowed lifecycle increment.

`reuseDenials` is a **pure diagnostic model**, not an authorizer. Even an empty result does not authenticate observations or prove live no-effect provenance/current grants. Synthetic positive fixtures are not trusted producer evidence. No runtime consumer or public observation-to-authority minting function exists. Later source-owned producer/transaction adapters must establish the evidence and lineage; unsupported histories fail closed rather than being recaptured under old approval.

## Version and expiry obligations for later persistence

| Event | State/version contract |
| --- | --- |
| Request decision | Current owned run/fence and exact current task version; end run paused, Doing→Waiting, increment task/new proposal once, create approval version 1; no new run |
| Approve | Current assigned human/session/CSRF, all current expected task/proposal/approval versions and now before expiry; pending→approved, Waiting→Ready; changed task/approval increment once, proposal unchanged |
| Reject | Same current human/version checks; pending→rejected, Waiting→Backlog; changed task/approval increment once; no automatic retry |
| Pending expiry | At now≥expires_at mark expired and retain Waiting with actionable state; increment changed observable task/approval once; no renewal |
| Approved but not dispatched expiry | Proposed explicit extension: remove claim eligibility and return Ready→Waiting with expired approval; retain history. Persistence/flag integration requires review before activation |
| Claim / known-no-effect failure | Fresh run/fence and ordinary task lifecycle version increments; original approval/proposal/expiry unchanged; reuse also needs genuine no-effect evidence, current bindings and remaining retry budget |
| Expiry after dispatch | Prevent new authorization/reuse but retain actual in-flight/outcome evidence; never infer cancellation or no effect. Settlement under expired approval requires explicit runtime integration |
| Cancel / permitted requeue | Invalidate approval authority and preserve history; current authorization/state/version checks remain; cannot clear uncertainty or renew approval |
| Replay / repeated sweep / terminal no-op | No repeated state increment, event, retry charge or new run; current access precedes replay |

This table is a reviewed contract target, not implemented SQL, alarms or race evidence. An expired Waiting task has explicit authorized cancel/replacement recovery; no silent renewal endpoint. Native requests still require bearer/runtime proof and current lease/fence; human decisions still require verified session/CSRF/current assignment. None of these helpers bypasses those existing closed routes or completes a task.
