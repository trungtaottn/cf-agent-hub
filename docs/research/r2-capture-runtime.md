## Measured RED to bounded implementation

The initial SQL approach fetched200 full rows and only then halved the encoded page. A real Workers regression measured **3,994,184 raw bytes materialized in one query**, exceeding the intended page-sized materialization budget even though the final chunk was bounded. The revised regression observed a peak 161,694 raw bytes / 10 rows materialized while capturing 203 rows containing 4,020,000 payload bytes. The revised query first selects at most200 integer row IDs and raw size scalars, chooses a conservative escaped-size prefix, and only then reads those rows. A row whose raw-size lower bound already exceeds1MiB fails before full materialization; actual canonical encoding still enforces1MiB. This is a query/result-byte observation, not a JavaScript heap measurement.

Other meaningful negative probes reproduced: current schema initially unavailable; generation mapping omission; missing last SQL receipt; simultaneous hash replay; changed producer/binding identity; conditional put refusal leaving a source reader stalled; SQL arrayBuffer trusting declared size; HMAC signing after proof expiry during key import; initial job hash adopting changed fence/handles; and inconsistent retained attachment edges. Fixes preserve failed receipts and prove that no signed complete manifest or open admission results from these failures.

The current SQL reader allocates at most the expected1MiB buffer and validates actual bytes. Artifact copy holds one producer chunk and emits digest/output slices at most64KiB with serial backpressure. A blocked source reader is cancelled by the operation-owned abort signal when a conditional put returns null or rejects. Size/checksum metadata alone never counts bytes. Verification rereads the actual destination after copy and again before publication.

## Final-pass ceilings versus observed feasibility

Independent sizing found a minimal current artifact entry at least530 canonical bytes and minimal SQL metadata entry at least130. Even ignoring every other manifest field, `530*A + 130*C <=65536`, with `C<=256`, implies at most316 artifact-plus-SQL get operations in the final pass; the real envelope is stricter. Independent maxima1000+256 cannot simultaneously fit the manifest. Current [Workers limits](https://developers.cloudflare.com/workers/platform/limits/#subrequests) and [DO limits](https://developers.cloudflare.com/durable-objects/platform/limits/) therefore do not establish a default subrequest-count overflow here.

A near-total-byte synthetic Workers study captured 31 immutable 8 MiB generations (248 MiB artifact bytes) plus 48,862 SQL bytes in 15 chunks. The revised run observed 91,795 ms capture time, 67,084 ms copying and 24,315 ms final readback, with a 22,235-byte manifest and maximum 23,380-byte whole job. The baseline failed safely after 505,422 ms during final readback when its operator proof expired; it is not counted as successful capture. Neither proof lifetime nor test timeout was increased. The test uses one real product-created generation and additional rows with that exact shape; it is a recovery byte-path study, not a product-ingress scalability benchmark. Source/bucket test runtime and host scheduling differ from deployed CPU accounting. Final receipt values are recorded in the [execution evidence](../r2-task-plans/issue-039-execution.md); only successful observed runs may be cited.

The initial near-ceiling experiment exposed costly repeated full inventory/chunk-receipt validation at every stream await. The revised guard pins an admission-validated exact serialized job baseline and compares every authoritative persisted row field while still freshly checking proof, installation, fence, barrier, producer and handles. Full strict typing and SQL receipt coverage remain mandatory at admission, counted completion and before HMAC/publication; a changed diagnostic also conservatively aborts. This removes repeated full parsing, not reauthorization. Baseline and revised observations must remain separately attributed.

Final readback is one bounded RPC and restarts after interruption. Near-ceiling success in the local runner cannot guarantee deployed30-second CPU feasibility, proof-duration headroom or production throughput. Any proof/fence/limit failure leaves the source closed and capture incomplete. If deployment evidence requires batching the final verification pass, that needs a reviewed durable cursor without changing concatenated SQL digest meaning or weakening manifest-last publication. No performance SLO is inferred.
