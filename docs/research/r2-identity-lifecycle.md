## Official research and choice

Cloudflare Web Crypto documentation describes CSPRNG-backed getRandomValues and asynchronous SHA-256 digest:
https://developers.cloudflare.com/workers/runtime-apis/web-crypto/

Cloudflare SQLite storage documentation requires transactionSync callbacks and storage operations to complete synchronously and documents rollback on thrown exceptions:
https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/

Cloudflare Durable Object state guidance says synchronous SQLite calls do not yield the event loop:
https://developers.cloudflare.com/durable-objects/api/state/

Choose prepared 32-byte opaque token plus hash outside SQL, with current authority/admission and business checks inside the existing synchronous command transaction. Keep raw token only in the private request-local closure; the descriptor returns token:null/revealed:false, and only a successful post-transaction firstExecution signal permits the response projection. This is directly compatible with `src/storage/transaction.ts:8-21` and `src/workspace/commands.ts` canonical persisted outcomes. No return or log path should include the raw token on errors.

Reject async crypto inside transactionSync: it violates the documented API and the repository's ASYNC_TRANSACTION guard. Reject persistent encrypted-token recovery: it violates one-time semantics, adds key management and enlarges recovery exposure. Reject a separate issuance endpoint/transaction: it splits domain/replay/event commit and permits orphaned or duplicated effects. A preflight replay lookup may avoid unnecessary entropy but cannot be authoritative; the final transaction must still arbitrate same-key races. Preparing an unused candidate secret on a replay is not issuing a credential, provided it is neither stored nor revealed.
