# R1 operator recovery protocol

Status: Specified contract · Implementation pending.

The [static credential runbook](r1-static-credentials.md) describes the implemented authenticated installation boundary. Capture/restore remain separate Task 11 acceptance work. This runbook defines the proposed first recovery implementation for workspace SQL, messages and outbox. It is not a completed backup or release procedure. The [command schema](../../spec/recovery-command.schema.json), [manifest schema](../../spec/recovery-manifest.schema.json) and [example set](../../examples/recovery/r1-commands.json) fix finite request shapes. The operator gateway is a separately deployed Worker at an exact protected HTTPS origin, never a route or binding on the public product Worker.

## Operator admission and commands

The CLI loads exact origin and environment/workspace allowlist from protected operator configuration and sends `CF-Access-Client-Id` and `CF-Access-Client-Secret` from a protected file or descriptor on every request. It refuses redirects and does not rely on a `CF_Authorization` cookie. The gateway validates the Cloudflare Access service assertion signature, configured issuer/audience, `type='app'`, time claims and signed `common_name` service-token client ID against the explicit operation/target allowlist. Service-token `sub` is empty; a human JWT, caller header, product session or bearer is not authority. Access Service Auth policy, provider availability and operator allowlist are all required. Verified operator identity and target/epoch form an internal `RecoveryOperatorContext`; untrusted JSON cannot supply it. Only the separate gateway invokes binding-only WorkspaceDO recovery methods. Install uses the same attribution.

`POST /operator/recovery` accepts exactly `install,capture,read-chunk,restore,write-chunk,verify,probe,resolve-delivery,retire,resume,status`. The closed envelope requires `operation,workspace_id,capture_id,expected_authority_epoch,operation_id,reason,payload`; capture ID is null only for install/probe. Identical `operation_id`/payload replay returns its original receipt only after rechecking current operator authorization; changed payload conflicts. JSON control envelope plus payload is at most 65,536 UTF-8 bytes. The payloads are respectively `{config,verification_bundle}`, `{budget}`, `{index}`, `{manifest,ledger}`, binary metadata `{index,sha256,byte_size}`, `{manifest}`, `{}`, `{delivery_id,disposition,evidence_sha256}`, `{}`, `{receipt_id,ledger,source_retirement_receipt,cutover_record}`, and `{job_id}`. No SQL, arbitrary table/object name or destination is accepted. Delivery resolution is a separately authorized operation: `confirmed_delivered` records trusted receiver receipt; `failed_without_redrive` leaves delivery permanently failed. Both require retained external evidence digest, create an immutable private receipt and create neither ACK nor another attempt.

Install compares `expected_authority_epoch` to current installed epoch (0 for empty authority), verifies config target matches authenticated environment/workspace and requires new `config_epoch` strictly greater than installed epoch; skipped epochs are permitted. Other operations compare installed epoch before starting and again before async completion. A stale operation fails closed. A different operation ID with identical already-installed material is a new non-advancing install and is rejected. Original matching install replays reauthorize before stale CAS, and verified service-proof expiry is checked after asynchronous preparation at SQL transaction entry. The signed-off protected bundle and current-authority ledger are outside captured SQL.

## Binary chunk transport

`write-chunk` uses `application/octet-stream`. `X-CFHub-Recovery-Control` holds unpadded base64url canonical UTF-8 JSON for the same closed envelope, with payload exactly `{index,sha256,byte_size}`. The encoded header is at most 8,192 ASCII bytes; index is 0–255, SHA-256 is lowercase 64-hex and byte size is 1–1,048,576. Authenticate service, target and installed epoch before accepting bytes; bound streamed bytes and verify actual length/digest rather than trusting Content-Length. `read-chunk` stays a JSON request with `{index}`; success returns `application/octet-stream` and `X-CFHub-Recovery-Chunk`, unpadded base64url canonical UTF-8 JSON of closed `{capture_id,index,sha256,byte_size}` under the same header and byte bounds. Ordinary responses/errors stay JSON receipt/envelope data. The CLI never logs row bytes. If platform header/body limits prove narrower, fail closed and amend this contract before transport.

## Capture and manifest

Establish a durable maintenance barrier before a checkpoint. It blocks domain mutation, login/session issuance, dispatch and destructive maintenance across restart while allowing restricted diagnostics. In-flight callbacks recheck barrier epoch before SQL updates. Drain admitted dispatch inside its lease or record unknown disposition; no completion crosses the frozen checkpoint.

Capture a versioned typed logical SQL export, not database-file bytes or arbitrary SQL. The runtime table registry must compare every table, column, type, primary-key order and restore mode against `sqlite_schema`; an unregistered item fails complete capture. The R1 registry is `schema_migrations,workspace_metadata,human_grants,static_agents,native_credentials,login_attempts,sessions,profiles,preferences,threads,thread_participants,messages,inbox,events,idempotency_outcomes,outbox,scheduler_state,maintenance_state,recovery_jobs,recovery_chunks,probe_receipts`. Domain/history IDs and event sequence remain stable. SQL pages have at most 200 rows; typed-row JSON tags binary as base64 and rejects unsafe integers/unknown columns. Each chunk has at most 1 MiB, each manifest at most 65,536 bytes and 256 chunks, and required operator budgets cap 1,000,000 rows and 268,435,456 bytes. Exceeding any bound yields failed/incomplete evidence, never a truncated complete manifest.

Freeze maintenance/job/chunk/probe control-record projections at barrier establishment and track capture work separately, avoiding recursive capture. Scheduler state is recomputed on restore. Login attempts/sessions restore revoked/consumed. Authority tables restore as history only until current-ledger overlay. Typed parameterized inserts into an empty isolated target are restart-safe by `(capture_id,table,chunk_index,digest)`; changed repeated chunk conflicts. Verify chunk digests/counts, complete registry and relationships before signing complete status. R1 artifact arrays are empty; future versions extend this manifest.

The manifest records format version 1, checkpoint, release binding IDs (unique 1–32 bounded identifiers, never secret values), the single captured workspace `{workspace_id,object_name}` catalog mapping, SQL counts/chunks and HMAC auth. Authenticate canonical manifest excluding tag with a dedicated operator-managed integrity key outside snapshots. Recovery files are AES-GCM encrypted under a different protected key, created exclusively 0600. Metadata stdout contains neither rows nor credential hashes. A complete receipt alone does not open admission.

## Restore, proof and resume

`CurrentAuthorityLedger` is independently authenticated and retained outside SQL. Restore requires latest approved ledger, with target epoch higher than manifest epoch and every recorded prior authority. Validate immutable credential actor/hash IDs, overlay current membership/restrictions/revocations and invalidate restored sessions/login attempts. Pending/in-flight notifications remain paused; absent trusted receiver receipt is unresolved, not evidence of nondelivery. Preserve attempt counts and replay history; never auto-redrive uncertain effects.

`probe` records a receipt only after actual transactional write/rollback and scheduling checks. Readiness reads this trusted receipt, not a caller-supplied assertion. `retire` writes a durable permanent barrier plus authenticated closed retirement receipt identifying source environment, workspace, epoch and barrier. A target `resume` requires matching authenticated source retirement receipt and cutover record, the latest external ledger, actual target catalog mapping, target epoch strictly higher than source and a fresh passing probe. Records prove reviewed linkage; they never create routing from supplied JSON. If source cannot be retired, fail closed for a separately reviewed outage-recovery procedure. Ordinary capture may resume its original unchanged source from its complete capture receipt if no target cutover/retirement occurred. In either path require zero unresolved effects, complete verified receipt and exclusive authority. `resolve-delivery` may record a trusted delivered receipt or explicit permanent failure, never a fresh attempt. Retirement prevents later source resume at that epoch. Keep private system-actor operator receipts outside restored state and never reenroll a principal silently.

Install control receipts use the permanent `operator.install` namespace in `idempotency_outcomes`, keyed by verified principal, workspace target and operation ID. Restore must exclude imported rows in this namespace and preserve the target's own active operator control history. Fresh request IDs and service-proof expiry are not part of the stable install-intent fingerprint.
