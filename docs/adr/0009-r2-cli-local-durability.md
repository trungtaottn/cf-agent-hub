# ADR0009 — Local CLI durability and protected provider

Status: Accepted for local MVP source development under delegated owner decisions D3/D-JOURNAL; deployed acceptance remains pending, with no released CLI package. Date: 2026-10-27.

## Decision and threat model

The native CLI groundwork uses separate `journal.sqlite` and `secrets.sqlite` files in explicitly selected private directories outside a checkout. The backend is Linux local SQLite through the pinned Node runtime's built-in `node:sqlite`; it adds no dependency. Exact owner, 0700 directory/0600 regular-file modes, single links, symlink-free trusted ancestors, live path/inode identity, closed application schemas and integrity checks are required. Existing insecure objects are rejected, not chmod/chowned. No operator/recovery credential helper is reused as a credential source or relaxed.

This is **owner-access-controlled plaintext**, not encryption at rest or an OS keychain. It protects against ordinary other-UID filesystem access under normal OS enforcement. Root, hostile same-UID/process code, compromised hosts, disk access, backups and snapshots are outside the threat model. Checksums detect accidental damage; they do not authenticate hostile rewrites. There is no arbitrary database/backup import or rollback API. Offline whole-store rollback by the same UID is not reliably detectable without an external trust anchor; an operator must use fresh setup/enrollment after an unsupported rollback. Code does not claim to detect or automatically force that action.

The supported source policy admits persistent local Linux ext-family filesystems (the ext2/ext3/ext4 shared statfs magic), XFS and overlayfs with operator-managed persistent backing. It rejects volatile tmpfs, network/FUSE and unknown filesystem types. Magic is a capability filter, not evidence that a mount survives host/container replacement. Operators must establish a persistent backing directory and storage that honors synchronization/locking. **Only overlayfs process-kill/reopen was exercised in this environment; ext-family/XFS hardware, reboot, power-loss and host replacement remain unverified.** Windows/macOS and actual vault adapters are unavailable, never plaintext fallbacks.

SQLite uses DELETE rollback journaling, EXTRA synchronization, bounded writer wait and immediate transactions. Effective settings are read back. EXTRA includes the directory sync after rollback-journal unlink; FULL alone does not establish that property. Precreation is exclusive, file and directory are synchronized, then the raw descriptor is closed before SQLite opens. Live checks never raw-open/close the DB because that can drop POSIX locks. Hot rollback journals are validated and left for SQLite recovery, not deleted as stale files. [SQLite atomic commit](https://www.sqlite.org/atomiccommit.html), [synchronization](https://www.sqlite.org/pragma.html#pragma_synchronous), [descriptor hazards](https://www.sqlite.org/howtocorrupt.html), [Linux fsync](https://man7.org/linux/man-pages/man2/fsync.2.html), [ext4 journaling](https://docs.kernel.org/filesystems/ext4/journal.html), [XFS logging](https://docs.kernel.org/filesystems/xfs/xfs-delayed-logging-design.html).

## Journal policy

An ordinary mutation records the complete validated semantic operation/method/encoded path/canonical query/canonical body/origin/workspace and authenticated provider binding. Intent creation precedes interactive key generation; compare-and-set key attachment precedes dispatch. Exact principal, slot/generation and provenance cannot silently change. A first-dispatch stamp commits before any fetch and never resets. The minimum server replay lifetime is 24 hours; local retention never extends it. Conflicts, invalid responses, timeouts and unknown outcomes stay unresolved.

D-JOURNAL bounds are 1,000 entries, 64 MiB logical reserved payload, 128 KiB complete entry, and 4 KiB reserved transition metadata per admitted entry. These are independent ceilings, not a physical disk quota: SQLite pages and rollback journals add overhead. Full admission fails without evicting unresolved intent. Explicit settled pruning is eligible after seven days; it is not automatic deletion or a maximum retention guarantee. Exact task/message content is sensitive and never copied to ordinary diagnostics. Outcomes retain only status, a fixed code and null request ID, never response bodies/headers/proofs. Known current credential/proof canaries and auth-shaped fields are rejected from journal inputs. The journal is not a generic DLP detector for arbitrary secrets embedded in user-authored text.

Linux `/proc/uptime` supplies suspend-aware BOOTTIME with conservative 10 ms precision allowance. A random process epoch deliberately proves only process-local continuity. Clock rollback, missing stamp, changed epoch or unproven continuity means no-send reconciliation. Wall time, same boot ID or `hrtime` alone do not authorize replay. A restart can recover a never-dispatched/keyless intent; **already-dispatched replay after process restart is unsupported by this adapter**, even if less than 24 hours appears to have passed. The retained record remains available for read/manual reconciliation. Actual suspend/reboot behavior was not exercised. [Kernel uptime implementation](https://github.com/torvalds/linux/blob/v6.18/fs/proc/uptime.c), [clock semantics](https://man7.org/linux/man-pages/man2/clock_gettime.2.html).

Final dispatch first finishes all SQLite/proof/currentness checks, then performs a trusted internal fresh-clock check immediately before fetch. Sampling before a potentially blocking writer lock is insufficient. The pure native transport remains Node-free; internal provider/clock registration belongs to the trusted implementation, not a public restore-by-JSON API. Hostile imports of internal modules are outside the same-process threat model.

## Proof and initial enrollment

The protected provider imports an opaque credential **unbound**; no token parsing, caller label or invented credential ID supplies a principal. Ordinary mutations remain unavailable until explicit authenticated enrollment captures a canonical RuntimeIssue. The actual pinned lease and native-private pending-capture registry bind the returned agent/workspace/runtime to origin, slot/generation and provenance. Staged proofs are not authority. A synchronous protected finalizer commits activation before safe success; aborted, timed-out or failed capture cannot activate a process receipt. Reopen validates protected state and restores that exact association; explicit rotation increments generation and requires fresh enrollment.

Initial enrollment cannot truthfully have a verified principal before its response. Its separate protected `EnrollmentAttempt` therefore records `principalId:null`, exact request/slot/generation/token digest and key, before sending. Its durable consumed mark precedes fetch. A consumed attempt never replays—even a crash before the actual fetch burns it conservatively. Fresh enrollment is explicit and uses a new recorded attempt; keys are unique in that store. Up to 1,000 attempts/64 MiB logical accounting are retained without silent eviction. One active and one staged proof are bounded; enrollment-attempt history is not an indefinite log.

Public client callbacks remain comparison/adapter hooks, not server authorization. Proof use is confined to a synchronous callback on the actual native lease. Asynchronous callback mistakes are observed and rejected without unhandled secret-bearing rejection. Public guards run before final currentness; only an internal verified clock capability runs afterward. All server scope, epoch, membership, proof and runtime checks remain authoritative.

## Alternatives and consequences

Atomic JSON replacement does not itself provide cross-process CAS; stale-PID/mtime locks can incorrectly steal from suspended writers. An append log requires custom framing, repair and compaction. SQLite supplies established transactional exclusion and crash rollback without a new package, though its pinned Node API remains release-candidate and synchronous operations can block the event loop. OS vaults may provide stronger guarantees but require an actually configured/tested adapter; none was authenticated or assumed here. A synthetic 100-write comparison is recorded in [research](../research/r2-cli-storage.md), not used as production throughput evidence.

The local source delivers persistence/provider/coordinator foundations, not a distributed CLI, interactive login/setup, raw-file replay, package provenance or operational acceptance. Issue44 owns the command surface and retained upload-file binding. No real credentials were read/imported/issued or ongoing account access configured. Integrated acceptance remains owner-deferred until after R4; predecessor issue40's blocked independent security signoff is unchanged.
